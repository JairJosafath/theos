## Context

Second step of `docs/plans/cel-lens-rule-view.md` (JairJosafath/cel-lens#2). `cel-lens.ruleList` answers every rule of the workspace and its compile state. A view needs to know when that changes, without asking for thousands of rules on each keystroke, and to show how far a scan of a big workspace is.

## Goal

The engine keeps a client's copy of the list current at the cost of what changed: each answer has a generation, a request can ask for what changed since one, and a notification says when there is something new and how far the scan is.

## Acceptance criteria

- [ ] Each answer of `cel-lens.ruleList` has a `generation`, a number that grows each time any file's entry changes. With `{"since": n}` it answers only the files whose entry changed after generation n, each whole, and `removed`, the URIs of the files listed at n and not now (deleted, no rule left, out of every folder, a Kyverno policy after `kyverno` turned off). An unknown or older `n` than the engine keeps, such as after a restart, gets the whole list with `"full": true`. A test applies a series of `since` answers to an empty list and gets the whole list.
- [ ] A client that sends `initializationOptions.ruleList: true` gets the notification `cel-lens/ruleListChanged` with `{generation, scan}`, never the list itself; another client gets none. For such a client the index starts at `initialize`, not at the first request.
- [ ] The index follows every change that changes a rule's entry, each covered by a test: an open file edited (after typing pauses, 250 ms, as the check of the examples waits), opened or closed (back to the disk's text); a YAML file or folder created, changed or deleted on disk (`workspace/didChangeWatchedFiles`); a `.cellens` change that types a value of a rule; the CRDs known changing (a policy typed from them); `kubernetesVersion`; the experimental features (`kyverno` adds or removes Kyverno policies, `crd-typed-policies` changes how policies are typed). A file whose entry did not change does not raise the generation.
- [ ] `scan` is `{state, yamlFiles, filesWithRules, filesLeftOut}`: `scanning` while the index walks the workspace (the first walk, and again after the version, the features or the folders change), `done` otherwise; the YAML files walked so far, those with rules, and the files the limits left out (past the 20,000th, over 1 MiB), as `cel-lens-core examples` counts them. During a walk the notification is sent at most every 500 ms and once when it ends; after a change, once.
- [ ] The answer and the notification are made on the message loop from what the background run found; the run never touches the session.
- [ ] `docs/engine.md` describes `since`, `removed`, `full`, the notification and `scan`; `CHANGELOG.md` has the entry.
- [ ] `go test -bench RuleListChange ./internal/lsp/` on the workspace of the `RuleIndex` bench (5,000 rules): one CRD file of 25 rules edited, from the end of the pause to the notification under 300 ms, the diagnostics budget; the `since` answer then holds that one file (its size reported). A change to a file with no CEL raises nothing and checks nothing.

## Out of scope

Example states: the next step. Folders added or removed: step 4 (this step's `scanning` covers them once step 4 sends them). The view.

## Notes

- `scan` gives the view its progress bar and its message (*Scanning: 4,210 YAML files read, 37 with rules*), and `filesLeftOut` its warning row; the words are the extension's.
- Keep the generation per session: the client tells a restarted engine by `full`.
