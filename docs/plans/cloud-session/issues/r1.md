## Context

Everything built for JairJosafath/cel-lens#6 is on GitHub `main`, and no release carries it. Releases were built in the Gitea of a factory on the owner's PC and copied to GitHub with the owner's token; that factory has published nothing since 4 November, and no session can hold such a token. A release must not wait for one machine. The plan is `docs/plans/cel-lens-releases-itself.md` in theos.

The front page of JairJosafath/cel-lens is `public-repo/` here. It has four workflows; `sign-release.yml` signs the files of a release and says nothing about how they were built, because it does not build them.

## Goal

A fifth workflow, `public-repo/.github/workflows/release.yml`, makes a release of the engine or of the extension from the source on `main`: it builds the files, tags, publishes, attests what it built, and leaves the release signed. A person, or a session, starts it by hand with the part and the version, and does nothing else.

## Acceptance criteria

- [ ] It runs only by hand (`workflow_dispatch`), with three inputs: the part (`engine` or `vscode`, a choice), the version (`X.Y.Z`), and optionally the commit to release, a commit of `main` and by default its head: `main` usually holds later work by the time a prepared version is released. Inputs reach scripts through `env`, never as an expression in a script's text.
- [ ] It stops before building, with a sentence saying what to do, when: the run did not start from `main`; the version is not `X.Y.Z`; the commit is not a commit of `main`; the release or either of its tags already exists; at that commit, for the engine, `engine/CHANGELOG.md` has no `## [X.Y.Z]` heading; for the extension, `vscode/package.json` does not name the version or `vscode/CHANGELOG.md` lacks its heading.
- [ ] It builds the source of that commit with the part's own `make dist` (the engine's six binaries and `checksums.txt`; the extension's `.vsix` files with the pinned engine), on the Go version of `engine/go.mod` or Node 24, as CI does.
- [ ] It creates both tags at the commit it built: `engine/vX.Y.Z` and `core-vX.Y.Z`, or `vscode/vX.Y.Z` and `vscode-vX.Y.Z`. Then it publishes the release of the second tag, named as the releases are today (`cel-lens core vX.Y.Z`, `cel-lens for VS Code vX.Y.Z`), with the files and that version's section of the changelog as its notes. An engine release is not marked latest; the extension's is, as today.
- [ ] It attests the build provenance of every file it built, and the attestation is a file of the release whose name ends in `.intoto.jsonl`, the name OpenSSF Scorecard looks for.
- [ ] After it, the release has the `.sigstore.json` signatures that the command in `SECURITY.md` accepts, with nobody starting a second workflow. (A release published with the workflow's own token does not start `sign-release.yml` through `release: published`.) `sign-release.yml` signs no provenance file.
- [ ] A failure leaves nothing half done that a second run cannot finish or that a person must delete by hand: say in the workflow's comments what a re-run does after each step that can fail.
- [ ] `permissions: read-all` at the top; each write permission is on the one job that needs it, with its reason beside it, as in `sign-release.yml`. Every action is pinned at the commit of its release, and Dependabot's configuration covers it.
- [ ] `SECURITY.md` (*Verifying a release*) gains the command that verifies a file's provenance and one sentence on what it proves that a signature does not. It says from which release on files carry it.
- [ ] `CONTRIBUTING.md` of the front page says how a release is made, in a few lines.
- [ ] Tests beside the other workflows' tests in `src/public_repo.test.ts` hold all of the above, the scripts driven against stand-ins for `gh`, `git` and `make` as the signing script's tests do. `CHANGELOG.md` has the entry.

## Out of scope

Preparing a version (the changelog and `package.json`): its own pull request each time. Publishing to the Visual Studio Marketplace or Open VSX: the publisher and its token are the owner's.

## Notes

- The workflow has never run when this merges. Say so in the pull request, and name what only the first real run can show.
- Check GitHub's and Sigstore's documentation for what you rely on (what the workflow's token may start, which identity a signature made in a called workflow carries, what `actions/attest-build-provenance` writes); don't go by memory.
- The source the workflow tags is what users get with `go install github.com/JairJosafath/cel-lens/engine@vX.Y.Z`.
