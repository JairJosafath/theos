## Context

Eighth step of `docs/plans/cel-lens-rule-hovers.md` (JairJosafath/cel-lens#4). The engine's hover is done (steps 1 to 6): one fixed order anywhere in an expression, its CEL in ` ```cel ` blocks, file text escaped, command links written only to the ids a client lists in `initializationOptions.hover.commands`, the **Fix** block without the message for a client that sends `hover.problems: fixes`, and `cel-lens.applyFix`. This step builds on v0.42.0 (JairJosafath/cel-lens#3) once it is merged.

Today the extension shows the engine's hover as it comes: no hover middleware, no `isTrusted` (a `command:` link would not run), no `supportHtml`, no `cel` language, so a ` ```cel ` block is plain text. The editor's CEL colours are the extension's (`ColorPainter`, `cel_lexer.ts`, `cel_styles.ts`). `vscode/docs/style/vscode.md` asks for hovers "rendered like the code" with "command links only to the extension's own commands (`isTrusted = { enabledCommands: [...] }`, never `true`)".

## Goal

In VS Code the hover's CEL is coloured as the editor colours it, its links run only the two cel-lens commands the hover needs, and a fix link applies the fix.

## Acceptance criteria

- [ ] One constant, `HOVER_COMMANDS`, is `cel-lens.applyFix` and `cel-lens.pickKubernetesVersion`. The extension sends `hover: {commands: HOVER_COMMANDS, problems: 'fixes'}` in `initializationOptions`; a test reads what is sent.
- [ ] A `provideHover` middleware rebuilds each `MarkdownString` of the engine's hover with `isTrusted` exactly `{enabledCommands: HOVER_COMMANDS}`, never `true`, and `supportHtml` set. A unit test holds both for a hover with and without CEL blocks.
- [ ] Each ` ```cel ` block becomes `<pre><code>` with one `<span style="color:#RRGGBB;">` per token, from the lexer `ColorPainter` uses and the palette of `cel-lens.colorStyle` for the hover's document and the active theme's kind (light, dark, `hcDark`, `hcLight`). Every span's `style` matches the form VS Code's hover sanitizer keeps (the regular expression of `markdownRenderer.ts` in VS Code 1.100, copied in the test with its source); every token's text is HTML-escaped (`<`, `>`, `&`, quotes); a `// …` comment after the code (`// -> true`) is left in the hover's text colour. With `colorStyle` `off` the block is left as the engine wrote it. Everything outside the CEL blocks is the engine's text unchanged. Unit tests for both styles in each theme kind, `off`, a string holding `<b>`, and a comment.
- [ ] `cel-lens.applyFix` (*Apply Fix*) is a command of the extension, hidden from the palette (`when: false`), as the commands that need an argument are, which forwards its argument to the engine with `runEngineCommand`; an error from the engine (the file changed since the hover) shows in the status bar for three seconds. A test against the stand-in.
- [ ] Each id of `HOVER_COMMANDS` is a command the manifest contributes; a test.
- [ ] e2e (`test/e2e/engine.test.ts`), with `CEL_LENS_SERVER_PATH` at an engine built from steps 1 to 6: on a fixture CRD with a near rule, a rule with a misspelled field and a description holding `[x](command:workbench.action.terminal.new)`, the hover with the extension's `hover` option has its sections in the plan's order, every `command:` link names an id of `HOVER_COMMANDS`, the description's link is escaped, the **Fix** block has no message; running `cel-lens.applyFix` with the near rule's link argument edits the document.
- [ ] `test/vscode.ts` gains only what the tests need (`MarkdownString.supportHtml`, `window.activeColorTheme`), typed with `satisfies` against the real API.
- [ ] `CHANGELOG.md` has the entry under *Unreleased*; the README is the last step's.

## Out of scope

Pinning the engine and the README's picture (the next step); a `cel` language or grammar (the plan's decision 9); colouring inline code.
