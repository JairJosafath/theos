## Context

Second step of `docs/plans/cel-lens-example-results.md` (JairJosafath/cel-lens#1). The engine knows a CustomResourceDefinition's examples, what each expects and whether the schema accepts it. Now the rules run.

## Goal

The engine runs each `x-kubernetes-validations` rule of a CRD on each of its examples with the API server's own validator, and a command answers the result per rule and example: allowed or refused, with the message the API server would return.

## Acceptance criteria

- [ ] The verdicts come from `k8s.io/apiextensions-apiserver/pkg/apiserver/schema/cel`, the validator the API server runs, for the Kubernetes version picked, after the defaults are applied, with the API server's cost limits. Nothing about a rule's meaning is reimplemented.
- [ ] Each result names its rule (the document, version and path of the rule, as the lines above the rules name it) and its example (file, line, `apiVersion`, `kind`, name), and says: `allowed`, `refused` with the API server's message and field path, `not run` with the reason (the rule does not compile, the rule's field is absent from the example, the example is not an update and the rule needs `oldSelf`), or `error` with the runtime error or the cost limit that stopped it.
- [ ] A rule under a list or a map runs once per item, as the API server does; the result gives each refusal with its own path.
- [ ] An example that is an update (the same object twice in one file) runs its rules as an update from the document before, so `oldSelf` is that document's value; a created example runs as a create. A rule with `optionalOldSelf` runs on both.
- [ ] Each result says whether it is what the example expects. An example that expects to be allowed and is refused by a rule is wrong at that rule. An example that expects to be refused is right when the schema or at least one rule refuses it (with a message part given, when a refusal's message contains it), and otherwise wrong on the example.
- [ ] `cel-lens.exampleResults` (`workspace/executeCommand`) answers for a file: per rule, its results; with a rule's location, only that rule's.
- [ ] Results are computed off the path of requests the editor waits for, kept until the rule, the schema, the example or the Kubernetes version changes, and stopped when the request is cancelled. The command waits for them; hover, completion and the lines never do. A bench with 100 examples and 50 rules sits beside the existing ones.
- [ ] `docs/engine.md` describes the command and what a result holds; `CHANGELOG.md` has the entry. `README.md` keeps dry runs under *Not supported yet* until a person can see a result in an editor.

## Out of scope

The part of the line above the rule, the hover and the warnings: the next step. Admission policies. A command-line check of the examples: a later step.

## Notes

- Tests hold the engine's verdicts to the API server's on real cases: for a table of CRDs and objects, the messages are the ones `ValidateCustomResource` plus the CEL validator give, including a rule with `messageExpression`, `reason` and `fieldPath`.
- The API server ignores a refusal of a value an update did not change (validation ratcheting, on by default since 1.33). Do what the picked version does, and say in the result when a refusal was ignored for that reason.
