## Context

The owner's request JairJosafath/cel-lens#1: while editing a rule, see what it says about example objects kept in the repository, without a cluster. The plan is `docs/plans/cel-lens-example-results.md` in theos. This is its first step: knowing a CustomResourceDefinition's examples and what each expects. No rule runs yet.

The engine already lists the documents of the workspace of a kind (`cel-lens.typeChoices`, `examples`), for *Give it a type*.

## Goal

For each CustomResourceDefinition it reads, the engine knows its examples: the documents of the workspace of a version the CRD serves, what each expects (allowed or refused), and whether the CRD's schema accepts it. A schema problem shows on the example.

## Acceptance criteria

- [ ] An example of a CRD is a YAML document of the workspace whose `apiVersion` and `kind` are a version the CRD serves, found as `typeChoices` finds them, with the same limits (100 examples, the workspace scan's file and size limits). The CRD's own file and a `.cellens` are never examples.
- [ ] Each example expects to be allowed, unless:
  - a folder of its path, or a word of its file name (split at `-`, `_` and `.`), is `invalid`, `bad`, `refused`, `rejected` or `denied`: then it expects to be refused;
  - the comment lines directly above the document's first key, or directly after its `---`, hold `# cel-lens: refused`, `# cel-lens: refused "part of the message"` or `# cel-lens: allowed`: the comment wins over the path. A `# cel-lens:` comment there that is none of these is a problem on that comment, saying the three forms.
- [ ] Two documents of one kind, namespace and name in one file are an update: the first is created, each later one is an update from the one before. The engine records which, for the step that runs the rules.
- [ ] Each example is checked as the API server checks a custom resource before its CEL rules: the CRD's defaults applied, then its schema's validation for the version the example names, on the Kubernetes version picked. Each problem is a diagnostic on the example, at the field it names (the nearest key that exists), with the API server's own message, severity error, source `cel-lens`. An example that expects to be refused and that the schema refuses gets no diagnostic for it: it is right.
- [ ] The diagnostics follow the files: editing, saving, creating or deleting an example, the CRD or a `.cellens` refreshes them, with the open documents' text winning over the disk, as the engine already does for `.cellens`. Closing an example leaves the diagnostics of the file on disk.
- [ ] `docs/engine.md` describes examples, what each expects and the schema check; `CHANGELOG.md` has the entry.
- [ ] Nothing here runs on the path of a request the editor waits for (hover, completion, the lines): a workspace with 100 examples of one kind does not make them slower (a bench beside the existing ones).

## Out of scope

Running the rules, the line above the rule, admission policies: later steps. A setting to turn it off: the step that adds the line.

## Notes

- `k8s.io/apiextensions-apiserver` holds the defaulting and the schema validation the API server uses; use them, do not write a second validator.
- A schema the CRD's own checks refuse gives no example diagnostics: the CRD's problem is already on the CRD.
