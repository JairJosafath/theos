## Context

Fifth step of `docs/plans/cel-lens-rule-hovers.md` (JairJosafath/cel-lens#4). The request: the cost "with the fix when there is one", and "hovering a problem shows the API server's message and, when there's a fix, a link that applies it". Links run only cel-lens's own commands.

The engine's quick fixes (`internal/lsp/codeaction.go`) are offered only for a diagnostic: *Change to `name`* and, for a cost error, *Add `maxItems: 100` to `spec.ports`*, sized by `sizer` (`pkg/check/size.go`) to bring the expression under its budget. The hover reads `initializationOptions.hover` (`commands`, `problems`) since step 1 and writes no command link yet.

## Goal

A rule at half its budget or more gets a fix sized to bring it under half, offered in the hover and the light bulb; a problem under the cursor gets its fixes in the hover's **Fix** block; and a link applies a fix through a new engine command, written only for a client that runs it.

## Acceptance criteria

- [ ] `sizer` takes the budget to bring an expression under. A near expression's fix is sized to half its budget: a table test where a rule at 60% over an unbounded list gets *Add `maxItems: N` to `spec.ports`* with N the largest of the ladder that brings it under half, and estimating again with the limit gives under 50%. No fix when every list, map and string it depends on has a limit. The over-budget fixes are unchanged: their tests pass unchanged.
- [ ] The near fix is a code action of kind `quickfix`, without a diagnostic, for a range that touches the expression, sized only when asked and kept with the version's costs; a rule under half gets none. A test through `textDocument/codeAction`.
- [ ] The **Fix** block lists each problem whose range holds the cursor, with a link per fix. With `hover.problems` `message` it holds the message first; with `fixes`, only the links, since the client shows the message itself. Without `cel-lens.applyFix` in `hover.commands`, each fix is named in words: *Fix: Add `maxItems: 1000` to `spec.ports` (a quick fix)*. A fix appears once per hover: an over-budget rule's is in **Fix**, and **Cost:** does not repeat it; a near rule's is in **Cost:**. Table tests for each.
- [ ] `cel-lens.applyFix` (`workspace/executeCommand`, declared by `initialize`) takes `{uri, version, range, title}`, works out the code actions the engine would answer for that range of that document now, and applies the one with that title with `workspace/applyEdit`, its label the title. A version that moved answers an error saying *the file changed since this hover; hover again*; an unknown title or a document that is not open answer an error; a client without `workspace.applyEdit` answers an error. LSP tests apply a name fix, an over-budget limit fix and a near fix and read the edited text.
- [ ] A link is `command:cel-lens.applyFix?` and the argument as a URI-encoded JSON array, titled with the fix's title, written only when `hover.commands` lists `cel-lens.applyFix`. A test decodes a link's argument and runs the command with it. Step 1's scan of every hover for `command:` links now sees these, and passes.
- [ ] `docs/engine.md` describes the command, the **Fix** block and the near quick fix; `CHANGELOG.md` has the entries.

## Out of scope

Fixing a schema total that is only near (the plan's decision 7 leaves it to each rule's own fix), the extension's command (step 8), changing the numbers an over-budget fix picks.

## Notes

- The `.cellens` commands already send `workspace/applyEdit` and wait for the answer (`pendingEdit` in `internal/lsp/command.go`); use the same path.
- The title is the code action's own, so the link applies exactly what the light bulb would.
