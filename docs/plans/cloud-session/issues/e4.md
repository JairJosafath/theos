## Context

The lines above each rule offer `Give it a type`, `Edit` and `Remove` for a `dyn` value (GitHub request JairJosafath/cel-lens#6). The engine owns the `.cellens` format, so the engine writes it; the VS Code extension only asks the person what type they mean.

## Goal

The language server answers `workspace/executeCommand` for four commands the client calls: list the type choices, check a type as it is typed, set an entry and remove one. Setting and removing edit the right `.cellens` through `workspace/applyEdit`, so the edit is undoable and lands in the editor's buffer.

## Acceptance criteria

- [ ] `cel-lens.typeChoices` returns the built-in kinds of the selected Kubernetes version and the CRDs of the workspace (group, version, kind), each with a one-line description.
- [ ] `cel-lens.checkType` with a type string returns no problem for a valid one and, for an invalid one, the message and the column, as the format issue reports them.
- [ ] `cel-lens.setType` with a value's keys and a `type` or `kind` adds the entry to the nearest `.cellens` in a folder above the file, or creates `.cellens` at the workspace folder's root with the header comment, or replaces the existing entry for that value; the file stays sorted by `file`, then document, then path.
- [ ] `cel-lens.removeType` removes the entry, and the file when it was the last one and nothing else is in it but the header.
- [ ] Each edit goes through `workspace/applyEdit`; a client that refuses it gets an error saying so, and nothing is written behind its back.
- [ ] Comments a person wrote in `.cellens` survive a set and a remove.
