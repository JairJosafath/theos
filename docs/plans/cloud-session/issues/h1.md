## Context

The owner's request JairJosafath/cel-lens#4: hovering a CEL rule, or any part of it, tells what is needed to trust it, in a fixed order. The plan is `docs/plans/cel-lens-rule-hovers.md` in theos. This is its first step: the hover's frame and its first section of the rule, the variables it uses.

Today the hover (`session.hover` in `internal/lsp/lsp.go`, `Assistant.Hover` in `internal/assist/assist.go`) answers only on a variable, field or function, plus the examples section of a CRD rule (`inline.ExamplesHover`); an operator, literal, string or space gets nothing. A schema's `description` goes into the hover unescaped. Why a value is `dyn` (`withDynReason`) shows only while `fitting-completion` is on.

## Goal

Every position inside a checked CEL expression gets one hover whose blocks always come in the plan's order (decision 1), its text from the file escaped, with the part under the cursor on top as today and a **Uses:** paragraph naming the variables the expression reads, their types, and why one is `dyn`.

## Acceptance criteria

- [ ] Every position inside an expression the check checks gets a hover: a CRD's `rule` and `messageExpression`; a ValidatingAdmissionPolicy's validation `expression` and `messageExpression`, match conditions, variables and audit annotation `valueExpression`; a MutatingAdmissionPolicy's match conditions, variables and mutations; a Kyverno ValidatingPolicy's, only while `kyverno` is on. Names, operators, literals, inside strings and spaces included. A position outside CEL, the YAML key (`rule:`) included, gets `null` as today. A table test has a position of each sort in each kind.
- [ ] A new package `internal/hover` renders the hover from its sections, in this order and no other: the part; the **Fix** block; then the paragraphs **Checks:** (or **Returns:**), **Uses:**, **Cost:**, **Examples:**, **Docs:**. Blocks are separated by `---`, paragraphs start with their bold label, and a block or paragraph with nothing is left out with no empty line or stray separator. A table test renders every combination of present and absent sections and holds the order. This step fills the part, **Uses:** and **Examples:**; the others are the next steps'.
- [ ] The range is the name when the cursor is on a part the hover describes, and the expression otherwise.
- [ ] The part block is today's hover text; the existing hover tests pass, changed only where escaping changes a description.
- [ ] Every text the hover takes from a file (a `description`, a name, a kind, a field path, a message) is escaped with one function, the one `inline` uses for the examples' text, moved where both packages reach it; a code span or fenced block is delimited by a run of backticks longer than any it holds. A table test: a description holding `[x](command:workbench.action.terminal.new)`, `<img src="https://example.invalid/a.png">` and `<span style="color:#f00;">`, a field name and a CEL string holding three backticks; the expected Markdown holds each only escaped or whole inside one code span or block.
- [ ] `initializationOptions.hover` is read: `commands`, a list of command ids (none by default), and `problems`, `message` (default) or `fixes`; another value is ignored with one `window/logMessage` line. A test helper finds every `command:` link in a hover's Markdown; one test runs every hover test table of `internal/lsp` with a client that lists commands and one that lists none, and fails on a link to an unlisted id. (No step writes a link yet; the test guards the later ones.)
- [ ] **Uses:** lists the variables of the scope the parsed expression reads, in the order first read, each once, without the comprehension's own variables: `self` (`Widget.spec.ports[]` and the schema's type, *the value the rule is on*, the subject words of the line above the rule), `oldSelf` (*the value before the update, so the rule runs only on update*), `object`, `oldObject`, `params`, `request`, `namespaceObject`, `authorizer`, each `variables.<name>`, and Kyverno's variables. A type `.cellens` assumes says so as the part hover does. A table test for a CRD's root, a nested node and a list's items, each policy kind, and an expression that reads no variable (no **Uses:**).
- [ ] A `dyn` variable or field says why, in **Uses:** and in the part hover, whether or not `fitting-completion` is on; `fitting-completion` gates only the completion. A table test shows each of the thirteen reasons of `internal/assist/dyn.go` with its sentence and the feature off. `pkg/feature`'s comment, the engine README's table of experimental features and `docs/engine.md` say what `fitting-completion` still does (the extension's README follows in its last step).
- [ ] `docs/engine.md` describes the hover's layout and the `hover` option; `CHANGELOG.md` has the entry.
- [ ] `go test -bench Hover ./internal/lsp/` before and after, in the pull request: within 10%.
