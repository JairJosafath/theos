## Context

cel-lens's core promise is information at the rule, like GitLens's line above each block (GitHub request JairJosafath/cel-lens#6, the owner's first priority). Where a value is `dyn` (a field with `x-kubernetes-preserve-unknown-fields` or no `type`, `params` of a custom kind with `crd-typed-policies` off, a Kyverno variable), the engine gives no checks and no completion, and the only fix today is to change the CRD. People should be able to tell cel-lens what such a value looks like, in a file they commit so their team shares it. This issue is that file's format and its reader; nothing uses it yet.

## Goal

A package in the engine reads a `.cellens` file (YAML, at any folder of the workspace) into entries, each a place where a value is `dyn` and the type cel-lens should assume there, and reports every problem in the file with its line. Each type converts to the engine's schema form (the OpenAPI-style maps `internal/assist` already builds), so a later change can use it. `docs/cellens.md` describes the format.

The format, which this issue settles:

```yaml
# .cellens: types cel-lens assumes where Kubernetes gives dyn. Commit it.
types:
  - file: config/crd/bases/widgets.yaml   # relative to this file's folder
    document: CustomResourceDefinition widgets.example.com   # kind and metadata.name
    version: v1                           # CRDs: the served version
    path: spec.config                     # the value, from the object's root
    type: "{name: string, replicas: int, labels: map(string, string)}"
  - file: policies/limits.yaml
    document: ValidatingAdmissionPolicy limits
    variable: params                      # policies: params, object, oldObject or variables.<name>
    path: spec                            # optional: a value under the variable
    kind: example.com/v1 Limit            # instead of type: a built-in kind or a CRD of the workspace
```

## Acceptance criteria

- [ ] A `.cellens` with entries like the two above parses into entries with their file, document, version or variable, path, and type or kind; a table test covers each field.
- [ ] `type` takes CEL's type names (`string`, `int`, `uint`, `double`, `bool`, `bytes`, `timestamp`, `duration`, `list(T)`, `map(K, V)`) and structs `{field: T, ...}` nested to any depth, and converts each to the schema form; a struct's fields are its properties, in the order written.
- [ ] Every problem names its line and says what to do: an unknown key, a missing `file` or `document`, both or neither of `type` and `kind`, `version` on a policy or `variable` on a CRD, a type that doesn't parse (with the column), a duplicate entry for the same value.
- [ ] An empty file and a file with only comments have no entries and no problems; a file that isn't YAML is one problem at line 1.
- [ ] `docs/cellens.md` describes the format with both examples, and the README links it.

## Out of scope

Using the types (checks, hover, completion), lines in the editor, writing the file from a command: later issues.

## Notes

- Keep it a pure package (no LSP) under `internal/`, with table tests.
- `internal/assist/scope.go` shows the schema maps a type must become (`obj`, `str`, `crdScope`).
- A path is dot-separated field names from the root of the object the rule or variable sees; `[]` steps into list items and `[*]` into map values.

## Dependencies

None.
