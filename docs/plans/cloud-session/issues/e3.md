## Context

GitLens puts a quiet line above each block ("1 author (zhuguoxi)"): always in the same place, useful at a glance, and clickable for more. The owner wants the same above every CEL rule (GitHub request JairJosafath/cel-lens#6), starting with the `dyn` values a rule uses, which `.cellens` can now type.

## Goal

The language server answers `textDocument/codeLens`: above each CEL expression it reads, one short line saying what matters about it, each part a command. The VS Code language client shows them with no client code.

## Acceptance criteria

- [ ] Above each rule (and `messageExpression`, policy `validations`, `matchConditions` and `variables`) one line: the type of `self` (or the policy's subject) and `compiles`, or the number of problems, for example `self: Widget.spec · compiles`.
- [ ] For each `dyn` value the expression uses, a part `self.spec.config: dyn · Give it a type`; clicking `Give it a type` runs the client command `cel-lens.giveType` with arguments naming the file, document, version or variable and path, as `.cellens` keys them.
- [ ] A value typed from `.cellens` reads `self.spec.config: {name, replicas} · Edit · Remove` (field names, cut with `…` past 40 characters), with commands `cel-lens.editType` and `cel-lens.removeType` and the same arguments.
- [ ] Lines are at most 80 characters; a rule with more than two `dyn` values shows the first two and `+N dyn`, whose command lists the rest.
- [ ] The setting `inlineInfo` (initializationOptions and `workspace/didChangeConfiguration`, default `true`) turns every line off and on without a restart.
- [ ] A document with 500 rules answers within the existing hover budget (a bench, not a test with a time bound); the commands' arguments are filled in `codeLens/resolve` if computing them costs more than the line itself.

## Out of scope

The commands' behaviour (the client's picker, writing `.cellens`): later issues. Example objects in the line: a later issue.
