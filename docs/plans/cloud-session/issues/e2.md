## Context

`.cellens` (the format issue this depends on) says which `dyn` values cel-lens should assume a type for. Nothing reads it yet. The owner's first priority (GitHub request JairJosafath/cel-lens#6) is that a `dyn` value, once given a type, gets checks, hover and completion like any typed one.

## Goal

The language server reads every `.cellens` in the workspace and uses its types: an expression whose value an entry names is checked, hovered and completed with that type. Problems in a `.cellens` show in that file. What is found only because of an assumed type says so, because the API server itself would not find it.

## Acceptance criteria

- [ ] With an entry typing `spec.config` of a CRD's `v1` as `{name: string, replicas: int}`, the rule `self.spec.config.replicas > 0` has no problem, `self.spec.config.nosuch == 1` gets a warning naming `nosuch` and `.cellens`, and completion after `self.spec.config.` offers `name` and `replicas`.
- [ ] The same works for `params`, `object`, `oldObject` and `variables.<name>` of a ValidatingAdmissionPolicy, and for a `kind:` entry naming a built-in kind or a CRD of the workspace.
- [ ] A problem that exists only because of an assumed type is a warning, never an error, and its message says the type comes from `.cellens` (with the file and line); the API server's own problems keep their severity.
- [ ] Hover on a value typed from `.cellens` shows the type and "from .cellens, line N".
- [ ] An entry applies only to the file, document and value it names, and to values `dyn` without it: an entry on a value Kubernetes already types is a problem in `.cellens` ("already typed as ...: remove this entry"), and the Kubernetes type wins.
- [ ] Problems in a `.cellens` (the format's, an entry naming a file, document or value that doesn't exist) are diagnostics on that `.cellens`, at the entry's line.
- [ ] Editing or saving a `.cellens`, or creating or deleting one, checks the open documents again, without a restart.
