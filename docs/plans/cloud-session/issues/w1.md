## Context

The owner's request JairJosafath/cel-lens#2: a cel-lens view that lists every CEL rule of the workspace and its state, a click from the rule. The plan is `docs/plans/cel-lens-rule-view.md` in theos. This is its first step: the engine makes the list. No view yet.

Today the engine knows a rule's problems only for a file that is open; a closed file gets only the problems the check of the examples finds. The workspace is walked by `walkYAML` (`internal/lsp/workspace.go`) for the CRD scan, the check of the examples and `typeChoices`, each with the same limits; none lists rules.

## Goal

`cel-lens.ruleList` (`workspace/executeCommand`) answers the documents with CEL rules of the workspace folders and the open files, and for each rule its identity, label, location, span and compile state: the state its file would show if it were open now.

## Acceptance criteria

- [ ] The documents listed are the ones `pkg/check` checks, no more: a CustomResourceDefinition of `apiextensions.k8s.io/v1`; a ValidatingAdmissionPolicy and a MutatingAdmissionPolicy of `admissionregistration.k8s.io`; a Kyverno `ValidatingPolicy` of `policies.kyverno.io/v1` only while `kyverno` is on, and not in an `evaluation.mode` the check skips. A `v1beta1` CRD, a ValidatingAdmissionPolicyBinding, Kyverno's other kinds and a document with no CEL are not listed. A table test holds each kind, in and out.
- [ ] A rule is one entry of a list holding CEL: an `x-kubernetes-validations` entry (its `rule` and `messageExpression` together); one item of a policy's `validations`, `matchConditions`, `variables` or `auditAnnotations`; one item of a MutatingAdmissionPolicy's `matchConditions`, `variables` or `mutations`. Each rule names itself as `cel-lens.exampleResults` names it (`document`, then `version`, `path` and `index`, or `field`, `name` and `index`) and has an `id`: the file's URI, `#`, and those parts. A second document of the same kind and name in a file gets `#2` after its name. A test shows the id unchanged when the rule's text changes and when a document or rule is added above it in another document.
- [ ] The `label` is, in this order, the rule's static `message`, a match condition's or variable's `name`, an audit annotation's `key`, else the expression on one line cut past 60 characters with `…`; `labelFrom` says which (`message`, `name`, `key`, `expression`). A `messageExpression` never labels. The words are made in package `inline`, with a table test of each case, an empty `message` and a multi-line block scalar among them.
- [ ] `location` is the expression's `{uri, range}`, the argument `cel-lens.showRule` takes; `span` is the range from the line of the rule's list item to the end of the item. Each document has its `range`, `kind`, `name` and the file's `file` below its workspace folder and `folder` (the deepest workspace folder holding it; none for an open file outside every folder).
- [ ] `compile` is `{state, problems, messages}`: `error` when a diagnostic of severity error of the file's check starts inside the rule's `rule`, `expression`, `messageExpression` or `valueExpression`, else `warning` for a warning, else `ok`; the count, and the first three messages with their severity. The warnings the check of the examples puts on a rule are not counted. A test holds, for an open file, the states to the diagnostics the server publishes for it, minus the example warnings.
- [ ] A closed file is read and checked in the background, never on the message loop: with `walkYAML` and its limits (20,000 YAML files, 1 MiB each, hidden folders and `node_modules` skipped, nothing outside the folder through a symbolic link), parsing only a file whose text has `CustomResourceDefinition`, `AdmissionPolicy` or, with `kyverno` on, `ValidatingPolicy`; with `check.Check` and the options an open document gets: the Kubernetes version, the features, the CRDs the session knows, the `.cellens` types of the file (made on the loop and passed in). An open file is the editor's text and the loop's own check of it. The answer's order is the folders', then the files' paths, then the file's.
- [ ] The index keeps, per file, what it read (by size and time) and the check it made, and checks a file again only when its text, the Kubernetes version, the features, the CRDs or the `.cellens` types it used changed. The first `cel-lens.ruleList` starts it and waits for it, as `typeChoices` waits for its walk; a later one answers from what it keeps after checking again only what changed. `$/cancelRequest` and `shutdown` answer as for the other commands. The run is a background run of its own like the check of the examples, not a command job, so it takes none of the four command slots.
- [ ] `initialize` declares the command; `docs/engine.md` describes it and its answer with an example; `CHANGELOG.md` has the entry.
- [ ] Benches beside the existing ones: `go test -bench RuleIndex ./internal/lsp/` on a workspace of 2,000 YAML files, 200 of them CRDs of 25 rules (5,000 rules): the first answer from an empty cache (reported), and an answer asked again with nothing changed (under 100 ms). `go test -bench RuleIndexRunning ./internal/lsp/` measures hover, completion and the code lenses of an open 1,000-line CRD while the index runs from an empty cache and while none runs: the worst wait is the same within noise, as `ClosedCRDs` shows for the check of the examples.

## Out of scope

Telling the client the list changed, answering only what changed, progress, files left out: the next step. Example states: step 3. Folders added or removed: step 4. The view: the extension's steps.

## Notes

- Checks of CRDs read the Kubernetes version from a setting of the whole process: use the guard the server's checks and the check of the examples share, so checks of one version run at once.
- The check of the examples also checks closed CRD files; sharing that check with the index is welcome when it is simple, and not required.
- A rule whose check is still to come is not listed with a guessed state: it waits for the check.
