# aws-lambda-py (Framework)

A serverless HTTP API on AWS in Python: a Lambda function using boto3 behind
an API Gateway HTTP API, keeping items in DynamoDB, with its infrastructure
as a CDK app in TypeScript. Nothing deploys: the check synthesizes the
CloudFormation offline. The same API as `aws-lambda-ts`, in Python.

- **Supports:** `function`
- **Layout:** `app/handler.py` (the handler `app.handler.handler`) creates
  boto3's DynamoDB `Table` resource at module scope, reads `TABLE_NAME` and
  passes each HTTP API event (payload 2.0, typed as a `TypedDict`) to
  `answer` in `app/api.py`, which routes `PUT` and `GET /items/{id}`,
  validates input and answers with status codes; `app/items.py` holds the
  rules and doesn't import boto3; `app/item_store.py` wraps the table
  behind the `ItemStore` protocol, and takes any object with boto3's
  `get_item` and `put_item`, typed with the `types-boto3` stubs. pytest
  tests in `tests/` use a fake store and a fake table; none calls AWS.
- **Infrastructure:** `infra/stacks.ts` exports `defineStacks(app: App):
  Stack[]`, which adds one stack named after the package (the Container):
  `infra/api_stack.ts`, with an on-demand DynamoDB table (KMS-encrypted,
  point-in-time recovery, deletion protection, `RETAIN`), a Lambda
  `Function` (Python 3.14, arm64, 256 MB, 10 s, JSON logs to its own log
  group kept one month, its own role granted only `GetItem` and `PutItem` on
  the table and writes to its log group), and an HTTP API with IAM
  authorization on every route, a throttled `$default` stage and an access
  log kept one month. It passes CDK Nag's `AwsSolutions` checks with no
  acknowledgement. `infra/api_stack.test.ts` asserts it with
  `Template.fromStack`.
- **Writes:** `pyproject.toml`, `uv.lock`, `.python-version`, `app/`,
  `tests/`, `package.json`, `package-lock.json`, `tsconfig.json`,
  `vitest.config.mts`, `cdk.json`, `infra/stacks.ts`, `infra/api_stack.ts`,
  `infra/api_stack.test.ts`, `README.md`, `CHANGELOG.md`, `.gitignore`
- **Python project:** `name` is the Container, version `0.0.1`,
  `requires-python >=3.14` (`.python-version` 3.14, which uv installs on
  first use), `[tool.uv] package = false`: nothing builds a wheel. boto3
  1.43.112 is the one `dependency`; the `dev` group pins ruff 0.16.10, mypy
  2.4.0 and pytest 9.1.1 (python-standard's) and `types-boto3[dynamodb]`
  1.43.112. pytest reads `tests/` with the repository root on the path.
- **Build:** the stack's code is `Code.fromAsset('app')` with local
  bundling: `uv export --frozen --no-dev` lists what `uv.lock` pins, and
  `uv pip install --target --no-deps --only-binary :all:` installs those
  wheels for `aarch64-manylinux_2_28` and Python 3.14 next to a copy of
  `app/`. boto3 ships in the bundle, not the runtime's copy. The local
  bundler returns true or throws, so CDK never falls back to Docker. uv
  reads its cache, which `uv sync` filled, or PyPI for a wheel the cache
  lacks. The asset's hash is its output's, so a change to `uv.lock` is a new
  asset. `cdk.json`'s `app` runs `infra/main.ts` with tsx, and its context
  holds the feature flags `cdk init` of aws-cdk 2.1145.0 recommends.
- **Tests:** pytest for the function; vitest runs `infra/**/*.test.ts` in
  Node, with 60-second test and hook timeouts for the tests that synthesize
  a stack (and bundle the function) in `beforeAll`.
- **Type check:** `tsconfig.json` is aws-lambda-ts's, including `infra` and
  `vitest.config.mts`; the Python is type-checked by the Standard's mypy.
- **Lockfiles:** `uv.lock` was generated by uv 0.12.23 and
  `package-lock.json` by npm 11 on Node 24; only the project's `name` is
  templated in each, so `uv sync --locked` and `npm ci` install exactly the
  pinned versions. `allowScripts` lets esbuild's install script run (tsx
  needs it).
- **Standard:** made for `aws-standard` v1.1.0 or later, which owns
  `infra/main.ts`, `infra/standard.ts`, `infra/standard.test.ts`,
  `ruff.toml` and `mypy.ini`. `package.json` lists its TypeScript tools with
  exact versions as aws-lambda-ts does, without esbuild, `@types/aws-lambda`
  or the AWS SDK.
- **Devcontainer:** `.c4factory/devcontainer.json` uses `c4factory/go:1.26`,
  the Go, Node and uv toolchain CI and agents use, with ruff, Python, ESLint
  and Prettier set up.

## How a template works

Everything in this repository is copied into the new Container repository at the
same path, except `.c4factory/`, which is input for the factory. Files ending in
`.tmpl` are rendered with Go `text/template` (missing keys are errors) and lose the
suffix; a `.tmpl` that renders to only whitespace is left out. Other files are copied
byte for byte. Paths are never rendered, only contents.

Data: `.Project`, `.SoftwareSystem`, `.Container`, `.DisplayName`, `.Type`, the chosen
`.Framework`, `.Standard`, `.Compute` and `.Deployment` (empty when none is chosen),
and `.Connectors` (sorted names). Functions: `has`, `snake`, `upper`, `lower`, `dart`,
plus the `text/template` builtins. No Python or TypeScript file is rendered: the
CDK app reads the stack's name and description from `package.json`.

Each path belongs to exactly one layer; `.devcontainer/**` and `.c4factory.yaml`
belong to the operator. Release a change by tagging a new version and bumping it in
`templates/versions.txt` of C4 Factory; a tag is never moved.
